# 已知问题与保留修复

## 交接时的限制

1. 数据停在 10 月 20 日，服务器恢复后的邮件、账号、续费或退款没有在此次离线分析中刷新。
2. 源代码后续改动大量未进入旧 Git；本次用运行目录实际文件创建新历史，旧 Git 的联系人种子和历史不会被带入。
3. 6 项 coupon Python 测试的最小 fixture 缺少 creator_profiles 等当前表，属于已知未修复错误。不能把其他检查通过写成全仓通过。
4. TypeScript 历史上有 Cloudflare/D1 类型和 implicit-any 诊断；是否在本副本仍存在以验证文件为准。
5. 当前 schema 是脚本逐步演进出来的，历史 migrations 不完整覆盖全部表、触发器和运营策略。正式迁移应以 schema checkpoint + 数据校验为起点，不盲目按日期跑 SQL。
6. 用码归因缺少可信事件源与独立创作者标识，无法可靠给出真实核销榜。
7. grant 分散在 operations 表、审计和轮次文件，不能把各来源条数相加成开通人数。
8. 本地 D1/Worker 曾间歇出现首页或 operations 500，SQLite quick_check 正常且自行恢复；没有证据证明根因永久解决。恢复时要看实际请求日志。
9. 公开活动证据和库存是硬约束，剩余 planned 数不等于今天可发人数。最近快照合格库存曾归零。
10. 既有跟进发送器、老个人 Gmail、不同回复日志及当前主发送器不是一个统一提交状态机；统一前须保留各路径未知保护与逐封证据。
11. billing-local 依赖仓库外 renewalSchedule.js、Stripe 私有配置和历史数据文件，副本默认关闭。它不会自动获得取消、退款权限。
12. 原部署是单机运营系统，硬编码发送身份、Keychain、launchd、Unix 锁和大 API 路由仍需工程化。不能宣称已是多租户、可直接横向扩容的平台。

## 已经存在且不能回退的修复

- 初次发送器在入口、每封、活动验证/数据库等待后、401 重试前重新检查同一个 ET 08–21 窗口。
- Google SMTP 按实际提交阶段分类：提交途中通信中断为 unknown；明确拒绝为 failed；已接受后 QUIT 失败保持 accepted。
- 中文“未送达”需要系统发件地址与真实增强 SMTP 状态码，不把普通客户引用错误认作退信。
- 最终 5xx Message expired 优先于同通知里的旧 4xx 重试历史，纯临时 DNS 故障仍为 delayed。
- 金额解析不把单独 $ 或空币种默认为 USD；套餐、起价、多条数量不强塞单项固定价。
- quote mention 标签有词边界，防止 mentioned 中引用一般预算被提取成对方 integration 报价。
- 编码空格/控制字符开头的收件地址被拦截，不自动解码并重发到猜测地址。
- durable hold 与 service case 用表和触发器保护，不因同步、过期、泛泛兴趣或导入旧 Sent 解除。
- Google 审核回复保留原线程、固定 Message-ID、独立间隔与锁；未知禁止自动重发。
- 全上下文哈希、最新 provider 收发、产品事实和精确经纪人归属必须发前复验；变化后完整重读。

## 本次副本特有的改动

真实联系人种子改为空；个人地址、租户/client ID、主机和本机用户名被脱敏；两份一次性实名操作脚本及其专用测试未导出。原脚本和测试其余逻辑保留。Python 凭证入口加入明确 opt-in，Microsoft ID 可用环境指定，默认 DB 可通过 VIDEOCODING_DB 配置；本地账单插件默认关闭。没有更改原运行目录或发送配置。

这些是交接隔离措施，不能把脱敏后的历史 redirects/skip 名单当作真实生产名单。生产部署必须使用安全交付的原始保护数据。
